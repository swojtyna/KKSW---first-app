# Phase 2 — UI Design Contract

> Visual and interaction contract for the app selection + blocklist review flow. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope:** Wire the existing Phase 1 `HomeView` "Choose Apps to Block" CTA into `FamilyActivityPicker`, add a "Blocked" review/edit screen with swipe-to-delete, and define the copy and empty-state rules for the persisted blocklist UI.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (native iOS / SwiftUI -- shadcn not applicable) |
| Preset | not applicable |
| Component library | SwiftUI native components only |
| Icon library | SF Symbols (system, no third-party icon packs) |
| Font | San Francisco (system default via SwiftUI `Font` API) |

**Inherits from Phase 1:**
- `Theme` enum (`DeluluDetox/Sources/DesignSystem/Theme.swift`) is the single source of truth for color. No raw `Color` literals allowed in views.
- 8-point spacing scale (`4 / 8 / 16 / 24 / 32 / 48 / 64`).
- Four typography roles mapped to SwiftUI built-in text styles.
- Electric violet `#7C3AED` as the single accent color.
- Native `ProgressView()` spinners, `buttonStyle(.borderedProminent)`, `RoundedRectangle(cornerRadius: 12)` for primary buttons.

**Phase 2 adds ONE boundary that Phase 1 did not have:** Apple's `FamilyActivityPicker` is a system-provided sheet. It is sheet-presented, never restyled. Apple controls its typography, spacing, and color inside the sheet -- our design contract applies only to the app-owned screens (`HomeView` and the new `BlockedView`) and to the sheet's presentation hosting.

**Hard rendering constraint:**
`ApplicationToken` / `WebDomainToken` / `ActivityCategoryToken` are opaque. Apps MUST be rendered with SwiftUI `Label(token)`. Apple does NOT expose app names or icons as strings/images. No custom app rows with `Text(name)` / `Image(icon)`. This is the single most important visual constraint for Phase 2.

Declared values (must be multiples of 4 -- unchanged from Phase 1):

| Token | Value | Usage in Phase 2 |
|-------|-------|------------------|
| xs | 4pt | Section header icon-to-text gap; row icon-to-label gap where applicable |
| sm | 8pt | Intra-row spacing; gap between section title and its label |
| md | 16pt | Default horizontal row padding; gap below list header group |
| lg | 24pt | Horizontal safe-area padding for empty state; padding above / below "Change selection" button |
| xl | 32pt | Vertical gap between hero SF Symbol and empty-state heading |
| 2xl | 48pt | Bottom safe-area offset for footer CTA |
| 3xl | 64pt | Top safe area to empty-state hero offset |

**Exceptions:**
- Minimum touch target 44x44pt per Apple HIG (swipe-to-delete gesture area inherits this from `List` + `.swipeActions`; "Change selection" primary CTA remains 50pt height like Phase 1).
- Apple's `FamilyActivityPicker` owns its own internal spacing; no override attempts.

## Typography

Unchanged from Phase 1 -- Phase 2 reuses the four roles. No new text styles introduced.

| Role | Size | Weight | Line Height | SwiftUI Style | Phase 2 Usage |
|------|------|--------|-------------|---------------|---------------|
| Body | 17pt | regular (400) | 1.47 (25pt) | `.body` | Empty-state subtext; "Change selection" button label |
| Label | 15pt | regular (400) | 1.33 (20pt) | `.subheadline` | Section headers inside `List` ("Aplikacje", "Kategorie", "Strony www"); accessory meta text |
| Heading | 22pt | bold (700) | 1.27 (28pt) | `.title2` | Empty-state heading ("Jeszcze żadnych wrogów") |
| Display | 34pt | bold (700) | 1.18 (40pt) | `.largeTitle` | Navigation bar large title ("Zablokowane") |

**Row labels rendered by `Label(token)`:** Apple controls the internal typography of token labels. Do NOT wrap with `.font(...)` overrides -- let Apple render at its native scale so names and icons stay legible. Apply `.font(.body)` only to text we own (headers, captions, buttons).

**Dynamic Type:** All text uses SwiftUI text styles -- scales automatically. The `List` layout accommodates Dynamic Type at AX sizes; rows reflow vertically without truncation. Do not hardcode row heights.

## Color

Unchanged from Phase 1 -- Phase 2 extends the existing palette. No new color tokens introduced.

| Role | Value | SwiftUI Usage in Phase 2 |
|------|-------|--------------------------|
| Dominant (60%) | `Theme.background` (`Color(.systemBackground)`) | `BlockedView` background; empty-state background |
| Secondary (30%) | `Color(.secondarySystemGroupedBackground)` | `List` grouped row surfaces (iOS default for `.insetGrouped`) |
| Accent (10%) | `Theme.accent` (`#7C3AED`) | See reserved-for list below |
| Destructive | `Color(.systemRed)` (`#FF3B30`) | Swipe-to-delete action background only |

**Accent reserved for (explicit list -- Phase 2):**
1. "Change selection" primary CTA button fill (full-width, 50pt, 12pt corner radius -- identical to Phase 1 primary button style)
2. Empty-state hero SF Symbol tint (`Theme.accent`, `.hierarchical` rendering mode)
3. Navigation bar tint for any back button chevrons on stack-pushed variants (system default if embedded in existing `NavigationStack`)

**Accent is NOT used for:**
- Row backgrounds or borders (rows stay on `secondarySystemGroupedBackground`)
- Section headers (use `Theme.secondaryText`)
- The "Change selection" affordance is a single point of accent on this screen -- do not additionally tint list icons or row chevrons with accent

**Destructive color reserved for:**
- Swipe-to-delete action background on each `TokenRecord` row (stock `.swipeActions(edge: .trailing) { Button(role: .destructive) }` -- iOS renders this red automatically)

**No new brand color.** Everything in Phase 2 uses what Phase 1 already shipped. If a requirement appears to need a new color, flag it to the user -- do not introduce one silently.

**Dark mode:** Semantic colors (`systemBackground`, `secondarySystemGroupedBackground`, `label`, `secondaryLabel`, `systemRed`) auto-adapt. `Theme.accent` is vibrant enough for both modes (Phase 1 rationale carries over). Full dark-mode QA remains a future-phase concern per Phase 1 UI-SPEC.

## Screen Inventory

Phase 2 adds exactly **one new app-owned screen** (`BlockedView`), wires an existing screen (`HomeView` CTA) into a system sheet, and reuses Apple's `FamilyActivityPicker` sheet. Three total flows below.

### Screen 1: `HomeView` -- rewired (no visual change)

**Purpose:** Entry point into the Phase 2 selection flow. Visuals unchanged from Phase 1 UI-SPEC §Screen 3. Only the action behind "Choose Apps to Block" changes.

**Phase 2 delta:**
- `HomeViewModel.chooseAppsTapped()` no longer a no-op. It toggles a `Destination?` case (e.g. `.picker(FamilyActivitySelection)`) that the view binds to a sheet presenting `FamilyActivityPicker`.
- **Once the user has a non-empty blocklist, `HomeView` MUST route to `BlockedView` instead of showing the empty hero.** The rule: if `blocklist.records.isEmpty` → empty hero (current Phase 1 state); else → `BlockedView`. Per Claude's Discretion in 02-CONTEXT.md, Phase 2's "Blocked" screen is the natural evolution of Phase 1's home empty state, not a separate tab. There is no bottom tab bar in MVP.

**Wiring contract:**
- `HomeViewModel` owns a `Destination?` enum (`@CasePathable`) with at minimum a `.picker(selection: FamilyActivitySelection)` case.
- `HomeView` uses a case-path binding (`$model.destination.picker`) to sheet-present `FamilyActivityPicker`.
- Dismissing the sheet commits the (possibly empty) selection via a UseCase call.
- After commit, `HomeView` re-evaluates the `isEmpty` branch and renders `BlockedView` if populated.

### Screen 2: `FamilyActivityPicker` sheet (Apple-owned, NOT restyled)

**Purpose:** User picks apps, categories, and websites to add to the blocklist. Requirements SEL-01 / SEL-02 / SEL-03.

**Visual contract:**
- Sheet presentation via `.sheet(isPresented: ...)` or `.sheet(item: ...)` in SwiftUI.
- Presentation detent: system default (full-height modal). Do NOT specify `.presentationDetents([.medium])` -- the picker needs full vertical space for three tabs (Apps / Categories / Web).
- **No custom toolbar, no custom background, no custom font applied to the picker itself.** Apple explicitly forbids restyling; the picker renders at OS-native fidelity.
- Sheet title, close/done affordances, search, and category tab bar: all Apple-controlled. We do not add a wrapping `NavigationStack` around the picker.
- The sheet MUST pre-seed the current `FamilyActivitySelection` so the user sees their existing picks when re-opening ("Change selection"). Pass the hydrated selection into `FamilyActivityPicker(selection: $selection)`.

**Interaction:**
- User adds/removes selections; the binding updates `selection` in real time.
- User dismisses the sheet (system affordance). ViewModel calls `UpdateBlocklistUseCase(selection)` which writes `blocklists.json` atomically.
- No app-owned "Save" button -- the Apple sheet's dismiss IS the commit trigger. This avoids a double-confirmation UX.

**Error / edge cases (see Copywriting):**
- Entitlement not approved: picker throws at presentation. Catch and present a fallback alert (see Error copy below).
- User authorization revoked between Phase 1 and Phase 2: `AppRootViewModel` already handles this via `scenePhase` recheck; Phase 2 trusts that guard.

### Screen 3: `BlockedView` -- new

**Purpose:** Review, edit, and remove persisted blocklist entries. Requirements SEL-04 / SEL-05. Shown in place of the Phase 1 empty hero whenever the blocklist is non-empty.

**Top-level structure:**
- Embedded in the existing `NavigationStack` from Phase 1 (no new stack).
- Navigation title: `"Zablokowane"` (Display role, `.navigationBarTitleDisplayMode(.large)` -- consistent with Phase 1 `HomeView`).

**Layout (top to bottom):**

1. **Large title area** -- system-rendered, owned by navigation bar.

2. **`List` with `.insetGrouped` style**, containing up to three sections. Each section appears only if it contains at least one record (no empty sections visible).

   | Section | Header copy | Rows |
   |---------|-------------|------|
   | Apps | "Aplikacje" | One row per `TokenRecord` where `kind == .application`, rendered as `Label(token)` |
   | Categories | "Kategorie" | One row per `TokenRecord` where `kind == .category`, rendered as `Label(token)` |
   | Web | "Strony www" | One row per `TokenRecord` where `kind == .webDomain`, rendered as `Label(token)` |

   Section order is fixed: Apps → Categories → Web. Rationale: apps are the most common / expected case for a self-control app; categories are broader; specific web domains are the power-user tail. This order matches user mental model.

3. **Row composition:**
   - Single cell = `Label(token)`. Apple renders icon + name. **No trailing accessory**, no chevron, no count badge. Keeping rows minimal signals "pure list, interact via swipe".
   - Row leading/trailing padding: system default for `.insetGrouped` (do not override with `.listRowInsets`).
   - Vertical padding: system default (~11pt). Do not set `.listRowInsets`.

4. **Per-row swipe-to-delete:**
   - `.swipeActions(edge: .trailing, allowsFullSwipe: true) { Button(role: .destructive) { ... } label: { Label("Usuń", systemImage: "trash") } }`
   - `allowsFullSwipe: true` -- a full swipe instantly deletes. Rationale per 02-CONTEXT.md Claude's Discretion: **no confirmation dialog.** Regret cost is near zero (user can re-pick via "Change selection"), and confirm dialogs for trivially recoverable actions create friction that punishes the engaged user.
   - Destructive button background is iOS-rendered red (no override).
   - On tap: ViewModel calls `RemoveTokenFromBlocklistUseCase(recordId:)` → writes `blocklists.json` atomically → animates row out (stock `List` animation, no custom).

5. **Footer CTA -- "Change selection":**
   - Rendered below the list, inside the same scroll container OR as a `safeAreaInset(edge: .bottom)` -- **choose `safeAreaInset(.bottom)`** so the button is always visible regardless of list length. Specify here to avoid executor ambiguity.
   - Full-width primary button, 50pt height, 12pt corner radius, `Theme.accent` fill, white bold text -- identical style to Phase 1 primary buttons.
   - Copy: `"Zmień wybór"` (see Copywriting Contract).
   - Leading/trailing padding: `24pt` (lg token).
   - Top padding inside inset: `16pt` (md). Bottom padding: `16pt` (md) above the home indicator (SwiftUI auto-respects safe area).
   - Tap: sets `destination = .picker(currentSelection)` → same picker sheet as `HomeView` opens, pre-seeded.

6. **Loading state (initial hydration):**
   - On first foreground, while `BlockedRepository` reads `blocklists.json` and reconciles tokens (`scenePhase == .active` reconcile per 02-CONTEXT.md D-05): show a centered `ProgressView()` with `Theme.accent` tint, no text.
   - Loading should complete in <100ms in practice (small JSON, few records). If a race makes the user see a flash, it's acceptable. No skeleton UI.
   - Loading covers the list area only; navigation title stays visible.

7. **Reconciliation state (`scenePhase == .active` after hydration):**
   - Silent. No spinner. Rows re-render if Apple's token rendering shifts (the opaque token is the stable identity; `Label(token)` re-resolves automatically).

**States summary:**

| State | Visual |
|-------|--------|
| Empty (`blocklist.records.isEmpty == true`) | Falls back to Phase 1 `HomeView` empty hero. `BlockedView` is NOT shown. |
| Loading (first open after cold start) | Centered `ProgressView()`, accent tint, no text |
| Populated | `List` with up to 3 sections + footer CTA visible |
| Error (read failure from App Group) | Inline error cell at top of list: icon `exclamationmark.triangle.fill` in `Color(.systemOrange)` + body copy (see Copywriting). Below: "Spróbuj ponownie" secondary button (text button, accent foreground, not filled). Below that: whatever records did load, if any. |
| Picker-presentation failure | Alert (see Copywriting). `BlockedView` content stays underneath. |

**Interactions:**
- Swipe row left → full-swipe delete OR partial-swipe reveal destructive button → tap to delete. Both commit immediately.
- Tap "Zmień wybór" → `FamilyActivityPicker` sheet opens with current selection seeded.
- Pull-to-refresh: **not implemented.** Reconciliation happens on `scenePhase == .active`; no user-facing refresh affordance. If the user force-quits and reopens, they see fresh state via the scenePhase hook.
- Tap on a row body (outside swipe): **no action.** Rows are not pressable. Rationale: there is no per-app drill-down in MVP (no per-app settings, no per-app stats). Surface remains simple.

## Navigation & State Contract

`HomeViewModel` extensions in Phase 2:
- Adds `blocklist: BlocklistSnapshot` observable property (or uses a child view model that owns it).
- Adds `destination: Destination?` where `Destination` is a `@CasePathable` enum:
  ```swift
  @CasePathable
  enum Destination {
      case picker(FamilyActivitySelection)
      case errorAlert(ErrorAlertState)
  }
  ```
- VM exposes intent methods: `chooseAppsTapped()`, `pickerDismissed(_ selection: FamilyActivitySelection)`, `retryPickerPresentation()`.
- VM does NOT import SwiftUI (CLAUDE.md rule). `FamilyActivitySelection` comes from `FamilyControls` which is non-UI.

A dedicated `BlockedViewModel` is acceptable if the home/blocked split grows too large for one VM; Claude's Discretion at planning time. MVP-minimum is to extend `HomeViewModel` and switch the sub-view inside `HomeView`.

`BlockedView` and `HomeView` empty state share a single parent container; they are alternate branches of `HomeView.body`, NOT separate stack destinations. The `NavigationStack` in Phase 1 stays a single stack.

## Transitions & Animation

| Trigger | Animation | Duration | SwiftUI |
|---------|-----------|----------|---------|

| Populated → empty (last row deleted) | Reverse crossfade: list fades out, empty hero fades in | 0.35s | Same |

No celebration animations, no haptics beyond what iOS emits automatically on swipe-delete, no bounces. Animation grammar is intentionally restrained to match Phase 1 UI-SPEC §Transitions.

## Accessibility Contract

| Requirement | Implementation |
|-------------|---------------|
| Dynamic Type | All app-owned text uses SwiftUI text styles. Rows reflow at AX sizes. `Label(token)` inherits Apple's Dynamic Type support. |
| VoiceOver -- row | `Label(token)` is Apple-provided; it ships accurate VoiceOver labels (app name). Do NOT override with `.accessibilityLabel` on the row -- trust Apple. |
| VoiceOver -- swipe-to-delete | Stock `.swipeActions` exposes a VoiceOver custom action named after the button label ("Usuń"). No extra wiring needed. |
| VoiceOver -- section headers | `Section(header: Text(...))` is auto-announced by VoiceOver. |
| VoiceOver -- CTA | Button label "Zmień wybór" is self-describing. |
| Minimum touch target | Swipe area = full row height (system); "Zmień wybór" button = 50pt; row tap-out-zones = N/A (rows not tappable). |
| Color contrast | Inherits Phase 1 -- accent #7C3AED on white is WCAG AA for large text; body and secondary text use system semantic labels. Destructive red on white is WCAG AA (4.5:1). |
| Reduce Motion | Crossfade transitions use `withAnimation(.easeInOut)` which SwiftUI auto-dampens under `UIAccessibility.isReduceMotionEnabled`. Stock `List` animations also auto-adapt. |
| Right-to-left layout | Not tested in MVP. Polish is LTR. `List` + `Label(token)` are locale-aware; swipe direction inverts automatically in RTL locales. |

**Accessibility anti-patterns to avoid:**
- Don't add `.accessibilityHidden(true)` to `Label(token)` -- it's the primary content of the row.
- Don't wrap token rendering in a custom view that overrides Apple's accessibility tree.

### Destructive actions

Per 02-CONTEXT.md Claude's Discretion: **swipe-to-delete is NOT gated by a confirmation dialog.** Regret cost is ~0 (user re-opens picker, re-selects). Adding a confirm dialog punishes engaged users with friction for a trivially recoverable action.

| Action | Destructive confirmation | Rationale |
|--------|--------------------------|-----------|
| Swipe-to-delete row | **None.** Full-swipe commits instantly. | Low regret, fast recovery via "Zmień wybór". iOS HIG: don't over-confirm reversible destructive actions. |
| "Change selection" that removes items via Apple's picker | **None** (Apple owns the picker UX). | Apple's picker is the commit surface; our app doesn't intervene. |

If usability feedback during Phase 1 human verification indicates accidental deletes, Phase 2 can revisit -- but MVP ships without confirm.

### Micro-copy rules

- Use full sentences with punctuation in body copy; fragments OK for UI labels.
- Contractions: Polish doesn't use them like English; use natural spoken register. Example: `Nie udało się` (neutral past impersonal) is fine, avoid stiff officialese.
- Never use "Ty" or "Proszę" formal register -- the project's tone is peer-to-peer, not customer-service.
- Do NOT add emoji to strings (per CLAUDE.md + project preference). Personality comes from word choice, not decoration.

## Theme Implementation Contract

Phase 2 introduces **no new Theme properties**. The existing `Theme` enum (Phase 1) covers all needs:

```swift
enum Theme {
    static var accent: Color       // #7C3AED
    static var background: Color   // systemBackground
    static var primaryText: Color  // label
    static var secondaryText: Color // secondaryLabel
    static var tertiaryText: Color // tertiaryLabel
}
```

If Phase 2 implementation hits a color need not covered by `Theme` (e.g. grouped surface, warning orange), add a new `Theme.*` property rather than using a raw `Color`. Document the addition in the plan and in `Theme.swift`.

**Additions expected in Phase 2 (suggested, at executor's discretion):**
- `Theme.groupedBackground: Color { Color(.secondarySystemGroupedBackground) }` -- for consistency with `List(.insetGrouped)` surfaces.
- `Theme.warning: Color { Color(.systemOrange) }` -- for inline error icon, distinct from destructive red.

These are suggestions, not requirements -- if the executor can deliver the screen without them by using `Color(.secondarySystemGroupedBackground)` directly, note the deviation and the planner decides.
