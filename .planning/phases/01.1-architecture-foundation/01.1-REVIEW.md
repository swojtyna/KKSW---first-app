# Phase 01.1: Code Review Report

**Reviewed:** 2026-04-19
**Depth:** standard
**Files Reviewed:** 28
**Status:** issues_found

## Summary

Phase 01.1 landed the Clean-Architecture foundation (DIContainer + distributed per-feature Injection files, Destination-enum AppRoot with Combine pipeline for Screen Time auth, mirror-layout tests). Overall the code is clean, small, and the dependency rules from CLAUDE.md are respected (VM → only UseCase, Repository not calling other Repositories, UseCases are thin pass-throughs, ViewModels only import `Observation`).

No critical (core-value-breaking) issues were found. `AppRootViewModel` correctly plugs `scenePhase == .active` into a refresh publisher so a revoked Screen Time grant propagates back to the router — the core-value hole the phase was designed to close is plugged.

Four warnings are worth handling before Phase 2:

1. **Combine `.sink` closure on `AppRootViewModel` writes MainActor-isolated state from the subject's thread without an explicit hop.** Works today because production call sites happen to emit from MainActor (the `OnboardingViewModel` awaits on MainActor, and tests emit from `@MainActor` tests), but this is load-bearing implicit behavior and explains the `Task.yield()` workaround in tests.
2. **`HomeViewModel` violates the project VM convention** — missing `@MainActor`, `@unchecked Sendable`, and even the `Observation`-only rule (HomeViewModel doesn't need them today, but it will the moment Phase 2 adds `PickBlockedAppsUseCase`, and asymmetry is exactly what CLAUDE.md memory flags as "dual conventions").
3. **Shared `DIContainer.shared` mutated from many test classes without parallel-execution guardrails** — flakiness waiting to happen once XCTest parallelization is enabled per-class.
4. **`DIContainer.resolve` fatalErrors on missing registration** — acceptable for fail-fast DI, but combined with `#Preview` blocks that call `DIContainer.shared.reset()` this becomes a real production crash vector if a preview ever runs alongside app code (or if a registration is forgotten after a future refactor).

Several info-level items (unused `OnboardingViewModel.error`, dead `MockScreenTimeAuthRepository`, dead `case .none` in `AppRootView`, tight race after `requestAuthorization`) are listed below.

## Warnings

### WR-01: `.sink` closure writes MainActor-isolated `destination` without explicit actor hop

**File:** `DeluluDetox/Sources/Features/Root/ViewModel/AppRootViewModel.swift:28-34`

**Issue:** `AppRootViewModel` is `@MainActor`-isolated, so writes to `destination` must happen on MainActor. The `.sink` closure captured in `init()` is `@Sendable` and runs on whichever thread the upstream publisher delivers on. The code works today because:
- `CurrentValueSubject` delivers the *initial* value synchronously on subscription, and `init()` runs on MainActor.
- `statusSubject.send(...)` in `ScreenTimeAuthRepositoryImpl.requestAuthorization()` is called after `try await AuthorizationCenter.shared.requestAuthorization(...)` from `OnboardingViewModel` / `DenialViewModel` (both `@MainActor`), so the continuation resumes on MainActor.
- `refreshStatus()` is invoked from `AppRootViewModel.refreshStatus()` on MainActor.

This is implicit and fragile. The test suite already needs `try await Task.yield()` between `subject.send(...)` and assertions (`AppRootViewModelTests.swift:6`) — the comment explains it as "Combine + Observation propagation" but the real reason is that the sink closure has no actor to hop to; it just runs inline. A future `DispatchQueue.global()` publisher (e.g., a background-delivered notification bridge in Phase 4 for shield deep-links) would silently produce MainActor violations / runtime warnings.

Under Swift 6 strict concurrency this write is diffused through `@unchecked Sendable` on the VM, which is exactly the kind of convention CLAUDE.md memory warns against ("no mętne reguły").

**Fix:** Hop to MainActor explicitly in the sink, or use `.receive(on: RunLoop.main)` / `DispatchQueue.main` upstream of the sink:

```swift
init() {
    observeStatus()
        .receive(on: DispatchQueue.main)
        .sink { [weak self] status in
            MainActor.assumeIsolated {
                self?.destination = Self.map(status)
            }
        }
        .store(in: &cancellables)
}
```

Or preferred (removes the need for `Task.yield()` in tests):

```swift
init() {
    observeStatus()
        .sink { [weak self] status in
            guard let self else { return }
            Task { @MainActor in
                self.destination = Self.map(status)
            }
        }
        .store(in: &cancellables)
}
```

(Trade-off noted: the `Task { @MainActor in }` variant is ordered but asynchronous; if ordering-vs-latency matters for the auth status pipeline, pick `receive(on:)`.)

### WR-02: `HomeViewModel` breaks project VM convention (dual-convention smell)

**File:** `DeluluDetox/Sources/Features/Home/ViewModel/HomeViewModel.swift:3-10`

**Issue:** Every other VM in the phase (`OnboardingViewModel`, `DenialViewModel`, `AppRootViewModel`) is declared `@MainActor @Observable final class … : @unchecked Sendable`. `HomeViewModel` is just `@Observable final class`. It happens to work because it has no async operations and no injected dependencies today, but:

- CLAUDE.md explicitly states "ViewModels use `@Observable` and never import SwiftUI" and the `@MainActor + @unchecked Sendable` pattern is the documented project rule.
- The moment Phase 2 adds `PickBlockedAppsUseCase` (the `#Preview` and Injection file both flag this), someone will retrofit `@MainActor` and trip the "why was this one different?" question.
- Per your MEMORY rule "no dual conventions / mętne reguły" — one rule that scales symmetrically is better than "rule X unless the VM is empty."

**Fix:**

```swift
import Observation

@MainActor
@Observable
final class HomeViewModel: @unchecked Sendable {
    func chooseAppsTapped() {
        // No-op in Phase 1 — wired to FamilyActivityPicker in Phase 2
    }
}
```

### WR-03: Shared `DIContainer.shared` mutated from test classes — parallel-run flakiness

**File:** `DeluluDetoxTests/Features/Root/AppRootViewModelTests.swift:18-29`, `DeluluDetoxTests/Features/Onboarding/OnboardingViewModelTests.swift:10-17`, `DeluluDetoxTests/Features/Denial/DenialViewModelTests.swift:9-18`

**Issue:** All three VM test classes call `DIContainer.shared.reset()` in `setUp()` and then register mocks into the global singleton. XCTest runs test *methods* serially within a class, but by default runs test *classes* in parallel across multiple child processes only when `Test parallelization` is enabled in the scheme — however, with Swift Testing/XCTest runner on Xcode 16+ this is becoming the default for new projects. As soon as any of these classes runs in the same process as another in parallel (or the Swift Testing runtime kicks in), one class's `reset()` will wipe another class's registrations mid-test. The failure mode is the `fatalError` in `DIContainer.resolve` (file:68) — i.e., the test *process* crashes, not just a failing assertion.

There is also no `tearDown` calling `reset()`, so a test class that fails halfway through leaves the container in a polluted state for any subsequent class in the same process.

**Fix:** Option A — inject a per-test container and thread it through the DI property wrappers (cleanest, but requires `@LazyInjected(container:)` overload). Option B — document the invariant and harden setUp/tearDown:

```swift
override func setUp() {
    super.setUp()
    DIContainer.shared.reset()
    // … register mocks
}

override func tearDown() {
    DIContainer.shared.reset()
    super.tearDown()
}
```

Plus explicitly disable parallel test execution for the `DeluluDetoxTests` target in `project.yml` / scheme settings, and add a comment in `DIContainer.swift` stating the singleton is not safe for parallel test runs. Option C — introduce `DIContainer.testContainer()` that returns a fresh instance and have the property wrappers read from a task-local override when present.

At minimum: pick one and document it in `.claude/guides/dependency-injection/GUIDE.md`. Currently the guardrail is silent.

### WR-04: `DIContainer` crashes (fatalError) on missing registration and `#Preview` blocks reset the shared container

**File:** `DeluluDetox/Sources/Core/DependencyInjection/DIContainer.swift:68-69`, `DeluluDetox/Sources/Features/Root/View/AppRootView.swift:40-50`, `DeluluDetox/Sources/Features/Onboarding/View/OnboardingView.swift:65-72`, `DeluluDetox/Sources/Features/Denial/View/DenialView.swift:64-69`

**Issue:** `DIContainer.resolve` calls `fatalError` on missing registration (line 68) and on wrong-type factories (line 79). For a bootstrap-only container this is defensible as fail-fast, but three things combine to make it dangerous:

1. Every `#Preview` block calls `DIContainer.shared.reset()` on the shared singleton. The comment in `AppRootView.swift:41-42` correctly notes "Preview mutates `DIContainer.shared`; fine because Xcode previews run in a separate process from XCTest." But Xcode previews can and do fire up in the *same* process as the app when running on a simulator and rebuilding — and previews for `AppRootView` register all four Injections, whereas previews for `OnboardingView` register only `OnboardingInjection`. If the app process picks up a preview-state container (it shouldn't under normal flow, but the risk surface exists), `resolve` crashes the whole app.
2. A future refactor that forgets to add a registration in `DeluluDetoxApp.init()` produces a crash at first `@LazyInjected` access — not at launch. This means a feature could ship with its `register(in:)` call missing and only crash when the user navigates into that feature.
3. The `fatalError` message quality is already good (includes fully-qualified type name), but there's no compile-time check that `DeluluDetoxApp.init()` registers everything consumed by `@LazyInjected` properties.

**Fix:** Two-part:

(a) Make `DIContainer.reset()` less universally-accessible — gate it behind `#if DEBUG` and a `testing` compile condition:

```swift
#if DEBUG
public func reset() {
    lock.lock()
    defer { lock.unlock() }
    storage.removeAll()
}
#endif
```

This guarantees release builds cannot have their DI container wiped by errant code.

(b) For missing-registration, at minimum log via `os_log` before fataling so the crash report in TestFlight / production carries the symbol:

```swift
guard var entry = storage[key] else {
    let message = "DIContainer: \(key) not registered. Check Injection files."
    os_log(.fault, log: .default, "%{public}s", message)
    fatalError(message)
}
```

(c) Longer-term: consider a compile-time registry via a macro that asserts at build time that every `@LazyInjected<T>` has a corresponding `register(T.self, ...)` somewhere — but that's Phase 2+ scope.

### IN-01: `OnboardingViewModel.error` is set but never rendered

**File:** `DeluluDetox/Sources/Features/Onboarding/ViewModel/OnboardingViewModel.swift:8`, `DeluluDetox/Sources/Features/Onboarding/View/OnboardingView.swift:6-62`

**Issue:** `OnboardingViewModel` exposes `private(set) var error: String?` and populates it in the `catch` branch of `grantAccessTapped()`. `OnboardingView` never reads `model.error` — no `.alert(...)`, no inline text, nothing. `OnboardingViewModelTests.testGrantAccessFailure` asserts on the value, but the user never sees it. `DenialViewModel` by contrast just logs and omits the property, which is the more honest state.

**Fix:** Either (a) render the error in the onboarding UI (`.alert("Authorization failed", isPresented: Binding(get: { vm.error != nil }, set: { if !$0 { vm.error = nil } })) { Button("OK") {} } message: { Text(vm.error ?? "") }`) to close the UX loop for `.denied` / `.notDetermined` after a prompt-dismissed, or (b) drop the `error` property and align with `DenialViewModel`. Picking (a) is more user-friendly for the "prompt dismissed" case where AppRoot won't yet have routed to `.denial`.

### IN-03: `case .none:` in `AppRootView.body` is effectively dead

**File:** `DeluluDetox/Sources/Features/Root/View/AppRootView.swift:26-29`

**Issue:** `AppRootViewModel.destination` starts as `nil` but the `.sink` fires synchronously on `init()` because `observeStatus()` is backed by a `CurrentValueSubject` that replays its current value on subscription. So by the time the first `body` evaluation happens, `destination` is already set (to `.onboarding`, `.home`, or `.denial` — never `nil`). The `case .none: Theme.background` branch is defensive UI that never runs in practice.

This isn't a bug (defensive placeholder is fine), but the comment "Przed pierwszą emisją statusu z repo — krótki placeholder" is misleading — there is no "before first emission" window in the current implementation.

**Fix:** Keep the branch but update the comment to reflect reality:

```swift
case .none:
    // Defensive: in practice CurrentValueSubject replays synchronously in init,
    // so destination is always set before first body evaluation. Kept as a safety net
    // in case the publisher pipeline changes (e.g., .receive(on:) introduces async gap).
    Theme.background
```

### IN-04: Tight race in `ScreenTimeAuthRepositoryImpl.requestAuthorization`

**File:** `DeluluDetox/Sources/Features/Onboarding/Repository/ScreenTimeAuthRepository.swift:25-28`

**Issue:** After `try await AuthorizationCenter.shared.requestAuthorization(for: .individual)` returns, the code reads `AuthorizationCenter.shared.authorizationStatus` and forwards it. The documented `FamilyControls` contract is that `requestAuthorization` only returns successfully when the status has been updated to `.approved`; it throws on denial or dismissal. So the read-after-await is effectively reading `.approved` in the success path. However:

- This is load-bearing assumption on an Apple framework with historically weak docs. If Apple ever changes `requestAuthorization` to return on `.notDetermined` (e.g., deferred prompt), the subject broadcasts a stale value.
- More importantly: `AuthorizationCenter` publishes its *own* updates via `authorizationStatus` KVO / async observer. If we're not subscribing to that source of truth, a status change from outside our flow (Settings revoke) only propagates when `refreshStatus()` is explicitly called. The phase covers `scenePhase == .active` (good), but a user toggling Screen Time in Settings *while the app is foregrounded* is invisible until the next scene activation.

**Fix:** Short-term (Phase 01.1 is fine as-is because `scenePhase .active` is the common trigger): document the invariant in a comment. Long-term (Phase 2+): subscribe to `AuthorizationCenter.shared` as an `AsyncSequence` / KVO source and pipe into `statusSubject`, so `refreshStatus()` becomes a debouncer rather than the sole source of updates. Track as a Phase 2 follow-up.

### IN-05: `@LazyInjected` without `@ObservationIgnored` is a latent crash

**File:** `DeluluDetox/Sources/Core/DependencyInjection/PropertyWrappers/LazyInjected.swift:10-30`

**Issue:** Every VM that uses `@LazyInjected` in the codebase is careful to prefix it with `@ObservationIgnored` (good). But nothing in the `LazyInjected` type enforces this. If a future VM writes:

```swift
@Observable
final class FutureViewModel {
    @LazyInjected private var thing: SomeUseCase
}
```

… the `@Observable` macro will attempt to generate observation hooks around the stored property, which (a) triggers `DIContainer.resolve` on every keypath observation (defeating lazy), and (b) can deadlock against `DIContainer.lock` if the observation tracking runs in a context that also holds the lock.

**Fix:** Document the rule explicitly in the header comment of `LazyInjected.swift` with a cautionary example. Consider a lint rule or `@preconcurrency` hint. Low priority because every current use site follows the convention, but the convention lives only in tribal knowledge.

### IN-06: `DIContainer.reset()` is `public` and always callable

**File:** `DeluluDetox/Sources/Core/DependencyInjection/DIContainer.swift:91-96`

**Issue:** Comment says "Testing only" but the method is `public` and has no gate. In a release build, any code (including third-party SDK if ever linked) can wipe the container. The `#Preview` blocks demonstrate this is not hypothetical — they call it routinely.

**Fix:** See WR-04 part (a): wrap in `#if DEBUG` or expose only via a `DIContainerTestHarness` type in a test-only target.
