# Phase 01.1: Architecture Foundation & DI Migration - Context

**Gathered:** 2026-04-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Przestawienie projektu z układu warstwowego (`Domain/`, `Data/`, `Features/<Feature>/`) + ręcznej `DependencyContainer` factory na układ **feature-first** z **`DIContainer`** i jasnymi regułami zależności (Repo ↛ Repo, UseCase → UseCase/Repo, VM → tylko UseCase, View → tylko VM). Refaktor 4 istniejących feature'ów (Onboarding, Home, Denial, Root) bez zmian funkcjonalnych — onboarding → auth → home flow z Phase 1 ma działać identycznie. Integracja `DIContainer` + property wrapperów z `to_integrate/`, aktywacja `swift-navigation` (pakiet jest w Package.swift od Phase 1 ale dotąd nieużywany), usunięcie `to_integrate/` i `DeluluDetox/Sources/App/DependencyContainer.swift` jako ostatni krok.

Granica wyznaczona przez ROADMAP.md Phase 01.1. Faza nie dotyka extensions targetów (DeviceActivityMonitor, ShieldAction, ShieldConfiguration) — tam jedynie baseline + regression check. Phase 2 (App Selection) zakłada nową architekturę i startuje po tej fazie.

<decisions>
## Implementation Decisions

### Navigation & Root State

- **D-01:** `AppRootViewModel` zależy **wyłącznie** od UseCase'ów — zero Repository. Stary wzorzec `container.screenTimeAuthRepository.authorizationStatus` usunięty.
- **D-02:** Nawigacja root-level przez `swift-navigation` `Destination?` na AppRootViewModel: `@CasePathable enum Destination { case onboarding, denial, home }` + `var destination: Destination?`. Enum **bez payloadu VM** — to zasadnicza różnica od wzorca modal (gdzie VM siedzi w enum case).
- **D-03:** Child view tworzy własny VM: `@State private var model = <Feature>ViewModel()` w OnboardingView / HomeView / DenialView. Child VM rezolwuje zależności przez `@LazyInjected` z `DIContainer.shared`. AppRootViewModel nie trzyma referencji do child VM.
- **D-04:** `Screen`-payload enum (`case onboarding(OnboardingViewModel)`) z `AppRootViewModel.swift:7-11` całkowicie usunięty. `screenTag` computed property (linia 14-20) znika wraz z nim — animacja wjazdu przechodzi na `.animation(value: destination)`.
- **D-05:** Aktywacja `swift-navigation` w 01.1 (nie Phase 2). Pakiet jest w `packages:` project.yml od Phase 1, ale dotąd nieużywany. Phase 2+ korzysta z tego samego wzorca (sheety, alerty, stack push — patrz navigation guide Wzorzec A).
- **D-06:** Odrzucone alternatywy: (a) Coordinator pattern — cofałoby świadomy wybór swift-navigation udokumentowany w CLAUDE.md; (b) Pure UC + custom Screen enum — zostawia dług "biblioteka w package, ale nieużywana", przy Phase 2 i tak trzeba by migrować.

### Event Flow (Combine statusPublisher)

- **D-07:** `ScreenTimeAuthRepositoryImpl` ma prywatny `CurrentValueSubject<AuthorizationStatus, Never>` zainicjalizowany aktualnym `AuthorizationCenter.shared.authorizationStatus`. Po udanym `requestAuthorization()` wysyła nowy status przez `.send(...)`.
- **D-08:** Repository eksponuje `var statusPublisher: AnyPublisher<AuthorizationStatus, Never>` przez `.eraseToAnyPublisher()`.
- **D-09:** `ObserveScreenTimeAuthStatusUseCase` w `Features/Onboarding/Common/UseCase/` zwraca `AnyPublisher<AuthorizationStatus, Never>`. Pattern Combine (nie `AsyncStream`) — bo `AsyncStream.makeStream()` jest single-subscriber, a `CurrentValueSubject` jest multi-subscriber + trzyma ostatnią wartość (nowy subskrybent dostaje aktualny status natychmiast, bez osobnego "get current").
- **D-10:** `AppRootViewModel`: `observe().sink { self.destination = map($0) }.store(in: &cancellables)`. `cancellables: Set<AnyCancellable>` oznaczony `@ObservationIgnored` (żeby zmiany w Set nie triggerowały observation invalidation).
- **D-11:** OnboardingVM, DenialVM i w przyszłości AppSelectionVM (Phase 2) subskrybują **ten sam** publisher przez ObserveUC — bez dodatkowej infrastruktury child→parent.
- **D-12:** `GetScreenTimeAuthStatusUseCase` (sync one-shot) **nie powstaje** — wycofany. CurrentValueSubject trzyma aktualną wartość; subskrypcja daje bieżący status natychmiast.
- **D-13:** `RefreshScreenTimeAuthStatusUseCase` w `Features/Onboarding/Common/UseCase/`, API: `func callAsFunction()` → woła `repository.refreshStatus()`. `ScreenTimeAuthRepositoryImpl.refreshStatus()` czyta `AuthorizationCenter.shared.authorizationStatus` i wysyła do `statusSubject.send(...)`. Zamyka scenariusz: user cofa Screen Time w Ustawieniach iOS → bez refresh AppRoot nie wie → UI pokazuje Home choć blokada nie działa = dziura w **core value**, nie kosmetyka.
- **D-14:** `AppRootView`: `.onChange(of: scenePhase) { _, newPhase in if newPhase == .active { Task { await model.refreshStatus() } } }`. `refreshStatus()` to metoda na AppRootViewModel wołająca `RefreshScreenTimeAuthStatusUseCase`.

### ViewModel Contracts

- **D-15:** `HomeViewModel` zostaje **pusty**, bez UC, bez `@LazyInjected`. Phase 2 doda pierwszy UC (np. `PickBlockedAppsUseCase`) i wtedy VM zyska pierwsze `@LazyInjected`. **Nie** dopisujemy wyjątku do `architecture/GUIDE.md` — reguła "VM → tylko UC (passthrough wymaga UC)" dotyczy VM przepuszczającego dane. Pusty VM nie przepuszcza niczego → przesłanka nie jest spełniona, nie ma czego wyjątkować.
- **D-16:** `OnboardingViewModel` i `DenialViewModel` przechodzą na `@LazyInjected private var requestAuth: RequestScreenTimeAuthUseCase` (i `observe`, `refresh` UC według potrzeby). Obecne `init(requestAuth:, onAuthorized:)` zastąpione przez `init()` bezargumentowy; callback `onAuthorized` znika (event flow przez Combine publisher, nie przez closure).
- **D-17:** Współdzielenie `ScreenTimeAuthRepository` między Onboarding i Denial: repo żyje w `Features/Onboarding/Common/Repository/` (Onboarding = feature-owner, pierwsze użycie). Denial wstrzykuje tylko UC, **nigdy repo** — egzekwowane przez VM→UC regułę.

### DI Container

- **D-18:** Pliki DI lądują w `DeluluDetox/Sources/Core/DependencyInjection/`:
  - `Core/DependencyInjection/DIContainer.swift`
  - `Core/DependencyInjection/PropertyWrappers/Injected.swift`
  - `Core/DependencyInjection/PropertyWrappers/LazyInjected.swift`
- **D-19:** `Core/` zarezerwowany dla infrastruktury cross-cutting (DI dziś, potencjalnie Logger/Analytics/Telemetry w przyszłości). Odrzucone: `Sources/DependencyInjection/` (top-level rozlewa Sources/), `Sources/App/DependencyInjection/` (semantycznie mylące — sugeruje "DI jest app-specific", a jest fundamentem).
- **D-20:** Jednorazowa rejestracja w `DeluluDetoxApp.init()` — wszystkie feature'y upfront:
  ```
  let container = DIContainer.shared
  CoreInjection.register(in: container)        // jeśli Core/ ma coś do rejestracji
  OnboardingInjection.register(in: container)  // repo, Request/Observe/Refresh UC
  HomeInjection.register(in: container)
  DenialInjection.register(in: container)
  RootInjection.register(in: container)        // jeśli AppRoot ma zależności
  ```
- **D-21:** Fail-fast: brak rejestracji → crash przy starcie, nie w środku nawigacji. Odrzucone: lazy per feature (race condition guards + skomplikowane testy bez realnego zysku — app nie jest modular), hybryda (dwie konwencje = mętna reguła).
- **D-22:** `ScreenTimeAuthRepository` scope: `.application` (singleton — trzyma CurrentValueSubject stan). `RequestScreenTimeAuthUseCase`, `ObserveScreenTimeAuthStatusUseCase`, `RefreshScreenTimeAuthStatusUseCase` scope: `.unique`. ViewModele **nie są rejestrowane** w DI (wrapper rezolwuje UC).
- **D-23:** Usunięcie `DeluluDetox/Sources/App/DependencyContainer.swift` jako ostatni krok planu po przejściu wszystkich feature'ów na `@LazyInjected` i zielonym buildzie.

<specifics>
## Specific Ideas

- **User explicitly preferuje aktywowanie zainstalowanych zależności nad wprowadzaniem nowych konwencji.** Rejection Coordinatora i Pure-UC+custom-enum podjęta z uzasadnieniem "zostawia dług biblioteki w package, ale nieużywanej" — swift-navigation zostało wybrane w Phase 1 świadomie, więc musi być realnie używane. Ta preferencja wpłynie na Phase 2+ (preferować use-what's-committed zamiast bring-in-new).
- **User rejectuje "dwie konwencje" / "mętne reguły" systematycznie.** Rejection hybrydy rejestracji ("mętna reguła, dług długoterminowy"), rejection dopisywania wyjątku do architecture/GUIDE.md dla pustego HomeVM ("nie ma wyjątku — jest trywialne niespełnienie przesłanki"), rejection centralnego Mocks/ przy feature-first source ("dwie reguły w głowie"). Planner i executor muszą trzymać pojedyncze, ostre reguły.
- **Combine wybrane nad AsyncStream z konkretnego powodu** — nie z inercji, ale bo `CurrentValueSubject` jest multi-subscriber + trzyma ostatnią wartość. `AsyncStream.makeStream()` jest single-subscriber; potrzebowalibyśmy osobnego kanału dla każdego subskrybenta albo `AsyncBroadcastSequence` zewnętrzny. Zachować Combine jako wzorzec dla **stanów globalnych** w projekcie (status autoryzacji, active sessions w Phase 3).
- **Core value (blokowanie apps) chroniona proaktywnie.** Decyzja D-13 (RefreshUC teraz, nie później) podjęta po zidentyfikowaniu scenariusza "user zmieni Screen Time w Settings → AppRoot nie wie → UI pokazuje Home choć blokada nie działa = dziura w core value". Decyzja D-30 (baseline + regression extension check) chroni core value przed cichymi regresjami w extensions. Oba = sygnał że user waży każdą decyzję przez pryzmat "czy to może złamać core value".
- **AppRootViewModel po refaktorze = wzorzec dla następnych root-level Coordinators.** Phase 4 (Shield Customization) prawdopodobnie potrzebuje tej samej struktury dla deep-link handling. Phase 5 (Scheduled Blocking) może mieć dodatkowy root state dla "active schedule now". Wzorzec Destination-bez-payloadu + scenePhase refresh + Combine publisher = szablon.
