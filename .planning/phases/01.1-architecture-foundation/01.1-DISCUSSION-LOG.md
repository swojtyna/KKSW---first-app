## Area 3: Wiring callbacków po LazyInjected

**Question:** Jak AppRootViewModel dowiaduje się o zmianie statusu autoryzacji (child VM → parent)?

| Option | Description | Selected |
|--------|-------------|----------|
| Closure przez view hierarchy | onAuthorized closure przez OnboardingView w konstruktorze; VM mutable property | |
| Streaming UseCase (Observe pattern) | AsyncStream + Repository publikuje zmiany; VM nie zna child | ✓ (z Combine) |
| scenePhase polling wystarczy | .onChange(of: scenePhase) .active → refreshAuthorization() | |

**User's choice:** Streaming pattern, ale **Combine zamiast AsyncStream**.

**Notes:**
- Combine chosen over AsyncStream bo:
  - `AsyncStream.makeStream()` jest single-subscriber
  - `CurrentValueSubject` jest multi-subscriber + trzyma ostatnią wartość
  - Subskrybent dostaje aktualny status natychmiast przy subscribe (bez "get current")
- ScreenTimeAuthRepositoryImpl: private `CurrentValueSubject<AuthorizationStatus, Never>` + `.send()` po `requestAuthorization()`
- `var statusPublisher: AnyPublisher<AuthorizationStatus, Never>` przez `.eraseToAnyPublisher()`
- `ObserveScreenTimeAuthStatusUseCase` w Features/Onboarding/Common/UseCase/ zwraca `AnyPublisher<..., Never>`
- AppRootViewModel: `observe().sink { self.destination = map($0) }.store(in: &cancellables)`
- `cancellables: Set<AnyCancellable>` z `@ObservationIgnored` (żeby Set mutation nie triggerował observation invalidation)
- OnboardingVM, DenialVM, AppSelectionVM (Phase 2) subskrybują ten sam publisher
- **Wycofano z Area 1:** `GetScreenTimeAuthStatusUseCase` (sync one-shot) niepotrzebny; CurrentValueSubject trzyma aktualną wartość
- Follow-up: mock ObserveUC zwraca `Just(status)` lub kontrolowany `CurrentValueSubject`

## Area 4b: Strategia rejestracji

**Question:** Kiedy rejestrować feature'y w DIContainer?

| Option | Description | Selected |
|--------|-------------|----------|
| Jednorazowo w App.init() | Wszystkie <Feature>Injection.register() sekwencyjnie w DeluluDetoxApp.init() | ✓ |
| Leniwa per feature | Guard + ensureRegistered() per feature przed @LazyInjected | |
| Hybryda krytyczne/lazy | Root+Onboarding upfront, reszta lazy | |

**User's choice:** Option 1 — jednorazowo w App.init(), wszystkie feature'y upfront.

**Notes:**
```
DeluluDetoxApp.init():
  let container = DIContainer.shared
  CoreInjection.register(in: container)
  OnboardingInjection.register(in: container)
  HomeInjection.register(in: container)
  DenialInjection.register(in: container)
  RootInjection.register(in: container)
```
- Fail-fast: brak rejestracji crashuje przy starcie
- Single source of truth: DeluluDetoxApp.swift = lista wszystkich feature'ów
- Deterministyczna kolejność
- Odrzucone: lazy per feature (app nie jest modular z dynamic features — race condition guards bez zysku), hybryda (dwie konwencje, mętna reguła "czy feature jest krytyczna?")

## Follow-up Area 6: Navigation guide — sekcja root-level state switch

**Question:** Navigation guide — sekcja 'root-level state switch'?

| Option | Description | Selected |
|--------|-------------|----------|
| Dopisać sekcję w 01.1 | Nowa sekcja: Wzorzec A modal vs Wzorzec B root-level | ✓ |
| Nie dopisywać | Traktować AppRoot jako jednorazową osobliwość | |

**User's choice:** Dopisać w 01.1.

**Notes:**
- **Wzorzec A — Modal (sheet, alert, push):** `@CasePathable enum Destination { case editProfile(EditProfileViewModel), ... }`; rodzic tworzy child VM w enum case; child VM umiera gdy case znika; dla wszystkiego co "otwiera się nad" aktualnym ekranem
- **Wzorzec B — Root-level state switch:** `@CasePathable enum Destination { case onboarding, denial, home }` bez payloadu VM; rodzic (AppRootViewModel) trzyma tylko Destination?; child view samodzielnie tworzy `@State var model = <F>ViewModel()`; child VM dostaje zależności przez `@LazyInjected`; dla app-level flow (onboarding vs main, paywall vs app, logged-out vs logged-in)
- **Kryterium:** child "nad" aktualnym ekranem (user wraca do poprzedniego) → A; child ZASTĘPUJE aktualny ekran (zmiana całego root contentu) → B
